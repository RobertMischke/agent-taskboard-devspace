Seven-day browser access

Pairing defaults to Remember this browser for 7 days. On the same local origin and browser profile, reload, reopening the browser and backend restart can resume access. The deadline is absolute and visits do not extend it. Log out revokes the remembered credential and associated runtime tokens for that browser. An unchecked option keeps only the current in-memory session.

The backend persists a credential hash privately. An HttpOnly, SameSite=Strict cookie is restricted to the session path; it alone cannot authorize project APIs. Browser enrollment, resume and logout require the exact origin and an intent header. API tokens stay in browser memory, outside URLs and localStorage. Definitive expiry returns all review components to pairing, with generation checks against late-response races. Reads may resume and retry once; writes and model starts are never replayed automatically.

Executed session checks: 34 backend, 16 UI-state and 18 real Chrome checks passed, including close/reopen, reload, new tab, logout, origin rejection and temporary mode. Isolated session/browser fixtures made no source, proposal or model writes. This proves the tested local workflow, not hosted-login or cross-browser qualification. Read the session contract.

Page and project review: Git-first design

Documented proposal, not an implemented evaluator: a page review should judge the complete page against its purpose, audience, positioning, supporting evidence and intended action. For Agent Studio, the initial context comes from selected authoritative files in agent-studio-marketing, pinned separately from product and website sources. Project-wide SEO, consistency and visual impression become bounded coding-agent tasks with structured results, coverage, limitations and follow-up actions. Visual evidence includes the route, viewport, locale/theme/state, capture time and actual rendered build identity. A screenshot alone does not prove a source revision; local Git does not prove the public deployment.

Git is the preferred source of record. Versioned portable context, task results and decisions reference repository identity, requested ref, resolved commit and file hashes. Explicit working-copy snapshots retain their in-scope content, untracked files and deletions. Accepted, kept, rejected and deferred judgments retain reasons and input revisions. Changes to source, goals or applicable decisions trigger revalidation; older records stay historical. Private host paths, credentials and raw runtime data stay outside portable public records. Persistence does not automatically commit or publish.

What still limits productive use

  • Editorial coverage: four advisory local rules, with no integrated LanguageTool, Vale, CSpell, Hunspell or textlint analyzer. No independent factual verification, calibrated voice score or automatic publication approval. Zero findings do not certify a text.
  • Source coverage: a task can propose 1-50 supported, non-overlapping text edits in one file. Dynamic/interpolated TypeScript, translation dictionaries, HTML attributes, structural and multi-file changes need separate implementation. Markdown is a supported subset. The original Quality Studio dictionary adapter remains unimplemented.
  • AI evidence: Runner transport and response validation exist; comparative DE/EN qualification, Token Economy admission and a guaranteed token or monetary ceiling do not. Valid spans and JSON do not prove meaning or facts are preserved.
  • Operating boundary: loopback, paired, local use. Source hashes, backups and recovery journals guard edits, but they do not provide an OS-wide lock against external editors. Avoid simultaneous edits during apply. Project checks execute trusted repository code with the host user's permissions. This is not an assessed shared or remotely hosted service.

Review, feedback and implementation

Browse → mark text → save feedback beside the source → inspect local or semantic findings → prepare a replacement → review the full source diff → explicitly apply → verify the changed running app or file. File/project reports cover the supported source inventory and declare exclusions. Feedback, proposals and run history persist in project metadata; stale versions cannot silently overwrite newer source.

The TypeScript adapter parses an AST without executing website code and preserves literal delimiters, escaping and Unicode. A task proposal can combine 1–50 non-overlapping supported text edits in one original file. Each quote and source mapping is validated; unsafe or overlapping edits reject the set. Syntax validation does not replace the website's Angular build/typecheck. Multi-file component changes remain a broader implementation task requiring their own affected-file plan and verification.

Saved tasks have explicit starts and outcomes

A task stores its instruction, selected feedback, source version, feedback revision and configured component-context fingerprint. Saving it does not start a model. An explicit, idempotent start uses the Coding-Agent-Runner. Source and context are checked again after the availability probe and before proposal creation or apply. The durable run claim prevents a retry from launching twice.

A validated combined proposal makes the task ready; a separate action applies the full reviewed diff. Task output declares changes, already_satisfied, needs_information or unsupported, with a concrete reason. Only already_satisfied without changes or open findings closes a task as retained text. Missing facts or an unsupported fix remain needs_review. A separate manual resolution needs a reason. Successful CLI exit alone is not evidence that the requested improvement was completed.

Task metadata under .voice-lint/tasks links the instruction, run and proposal. Failed, cancelled, interrupted and stale tasks remain visible and do not restart automatically. Applying uses the existing source backup and transaction recovery; source tasks cannot bypass their owning revision checks.

Explainable rules and local language-tool candidates

knowledge/rules.json supplies the four local rules and the wiki. Each rule explains its trigger, context questions, acceptable counterexamples, next step and limitations. A wordlist hit such as “powerful” or “leistungsstark” is a review prompt, not proof of a bad sentence. Qualified claims, personal positioning and dated evidence remain meaningful in their context.

Semantic review uses the Coding-Agent-Runner

The tool boundary is implemented through CodingAgentRunner 0.7.0. The explicit semantic-review action starts a configured local CLI route. The Runner receives a staged source snapshot, mapped units, feedback and bounded component context with read-only permission, clean context and delegation disabled. It returns structured findings with exact quote/span references and reasoning. It cannot apply source changes. Running, completed, failed, cancelled and stale results are stored and shown separately. Incomplete output fails validation and carries an explicit error instead of appearing as a complete review.

There is no model call during page opening or ordinary lint. A configured route is visible before starting; semantic review can use the operator's existing CLI account. Execution is not an automatic claim of Voice qualification, cost approval by Token Economy or a proven best model. Integration tests use fake Runner streams; their success must not be presented as a real model benchmark.
