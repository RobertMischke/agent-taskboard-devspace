Review, feedback and implementation

Browse → mark text → save feedback beside the source → inspect local or semantic findings → prepare a replacement → review the full source diff → explicitly apply → verify the changed running app or file. File/project reports cover the supported source inventory and declare exclusions. Feedback, proposals and run history persist in project metadata; stale versions cannot silently overwrite newer source.

The TypeScript adapter parses an AST without executing website code and preserves literal delimiters, escaping and Unicode. A task proposal can combine 1–50 non-overlapping supported text edits in one original file. Each quote and source mapping is validated; unsafe or overlapping edits reject the set. Syntax validation does not replace the website's Angular build/typecheck. Multi-file component changes remain a broader implementation task requiring their own affected-file plan and verification.

Saved tasks have explicit starts and outcomes

A task stores its instruction, selected feedback, source version, feedback revision and configured component-context fingerprint. Saving it does not start a model. An explicit, idempotent start uses the Coding-Agent-Runner. Source and context are checked again after the availability probe and before proposal creation or apply. The durable run claim prevents a retry from launching twice.

A validated combined proposal makes the task ready; a separate action applies the full reviewed diff. Task output declares changes, already_satisfied, needs_information or unsupported, with a concrete reason. Only already_satisfied without changes or open findings closes a task as retained text. Missing facts or an unsupported fix remain needs_review. A separate manual resolution needs a reason. Successful CLI exit alone is not evidence that the requested improvement was completed.

Task metadata under .voice-lint/tasks links the instruction, run and proposal. Failed, cancelled, interrupted and stale tasks remain visible and do not restart automatically. Applying uses the existing source backup and transaction recovery; source tasks cannot bypass their owning revision checks.

Explainable rules and local language-tool candidates

knowledge/rules.json supplies the four local rules and the wiki. Each rule explains its trigger, context questions, acceptable counterexamples, next step and limitations. A wordlist hit such as “powerful” or “leistungsstark” is a review prompt, not proof of a bad sentence. Qualified claims, personal positioning and dated evidence remain meaningful in their context.

LanguageTool, Vale, CSpell, Hunspell and textlint are evaluated integration candidates, not installed Voice analyzers. Grammar, spelling and editorial style need different mechanisms. Engine licenses are separated from dictionaries, models and rule packages. docs/language-tooling.md records the primary-source research; THIRD_PARTY_NOTICES.md and docs/licenses/npm-inventory.json record actual dependency metadata. The inventory has 603 resolved npm entries, including optional/platform packages; it is neither a browser-module count nor a complete file-level license audit. This research assigns no new license to first-party Voice code.

Semantic review uses the Coding-Agent-Runner

The tool boundary is implemented through CodingAgentRunner 0.7.0. The explicit semantic-review action starts a configured local CLI route. The Runner receives a staged source snapshot, mapped units, feedback and bounded component context with read-only permission, clean context and delegation disabled. It returns structured findings with exact quote/span references and reasoning. It cannot apply source changes. Running, completed, failed, cancelled and stale results are stored and shown separately. Incomplete output fails validation and carries an explicit error instead of appearing as a complete review.

There is no model call during page opening or ordinary lint. A configured route is visible before starting; semantic review can use the operator's existing CLI account. Execution is not an automatic claim of Voice qualification, cost approval by Token Economy or a proven best model. Integration tests use fake Runner streams; their success must not be presented as a real model benchmark.

Which models should Voice know?

Voice owns task-specific editorial qualification and preference. Token Economy owns the existing catalogue, model identities, capacity/cost knowledge and routing policy. The host owns configuration, credentials, admission and execution. The Runner is the execution mechanism, not another model-quality catalogue.
